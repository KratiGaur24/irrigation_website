## User journey

1. The existing entry opens Home and is labeled **Demo access · No sign-in**.
2. Confirmed absence of farms shows **Add Your Farm**. Enter a farm name, optional location, and a field name. A field is required by the existing crop-cycle relationship; no area, coordinates, sensor, or scientific values are invented.
3. An existing farm without fields shows **Add a Field**. Farmers can also select an existing farm under **More → Your Farms**. The header field picker shows fields belonging to that farm.
4. A selected field with a confirmed empty active-cycle response shows **Add Your Crop**. Choose an existing catalogue crop, enter its sowing date, and optionally enter an expected harvest date.
5. **Save and Continue** writes through FastAPI to PostgreSQL and returns to Home. Existing variety and production-condition controls remain on Crop.
6. A configured farm/field/crop opens the normal dashboard without forced onboarding. The seeded demo remains configured and is never cleared to demonstrate an empty state.
7. **More → Edit Farm** prepopulates the farm name and location. **Crop → Edit Crop** prepopulates sowing and expected harvest dates. Farm edits return to More; crop edits return to Home. Ownership, coordinates, relationships, variety, agronomic profile, stage fields, and other unrelated values are retained.

Browser storage remembers only the farm/field selection under `kisan-jal.selection`; the database remains authoritative for saved information. Saved data survives navigation and refresh. Unsaved entries survive asynchronous renders and language switches, but intentionally are not persisted across refresh or after leaving the form. Back cancels the form without deleting saved records.

Loading and failed reads do not trigger missing-data setup actions. Failed initial reads show a retry action. Failed writes retain form entries. If farm creation succeeds but field creation fails, retry uses the saved farm rather than creating it again; after a refresh that farm can be selected to complete field setup.

## Limits and unchanged behavior

- Browser visual verification could not run: browser inventory was empty and creating an in-app browser tab returned `Browser is not available: iab`. Desktop/mobile appearance still needs a manual browser check. The existing responsive grid and navigation styles were reused.
- This remains the existing shared demo application, without login, per-user isolation, or account registration. New farms use the existing configured demo owner. If that owner is absent, setup explains that the administrator must run the existing seed. No user is silently created. `DEMO_USER_EMAIL`, when customized, must match the email used when seeding.
- Crop choices come from the existing active catalogue; no crop records or scientific defaults are fabricated. Crop identity stays fixed during edits so its retained variety/profile associations are not reassigned. Variety and production conditions remain editable through the existing agronomic form.
- No dependency, database migration, new backend service, or state-management library was added. ESP32 firmware, irrigation automation, pump-control behavior, sensor calculations, and crop growth-stage calculations were not modified.
- Restart the backend if it is running without reload; Vite development mode reloads the frontend changes automatically.
